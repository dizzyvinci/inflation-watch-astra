INPUT SHAPE FOR AN ACTUAL SUPPORTED-BROWSER CAPTURE
{
  "sourceUrl": "https://mesos.watch/",
  "capturedAt": "<actual batch completion, timezone-aware>",
  "planHash": "<hash of the frozen incoming request plan>",
  "captureStartedAt": "<optional actual batch start>",
  "captureCompletedAt": "<optional actual completion; same instant as capturedAt>",
  "scannerFreshnessText": "<actual displayed context, if available>",
  "items": [
    {
      "requested": "<item name or exact ID requested>",
      "expectedItemId": "<positive integer copied from the frozen request plan>",
      "expectedItemName": "<expected item name copied from that plan>",
      "capturedAt": "<actual time this tool result returned>",
      "result": "<unmodified returned object or WebMCP text-content envelope>"
    }
  ]
}
The shown strings are schema descriptions, not a fabricated capture fixture.
The legacy direct-item shape remains readable. A missing per-item timestamp is
explicitly marked batch_timestamp_only; it is not promoted to an exact item time.
When expectedItemId/expectedItemName are supplied, the returned positive ID must
match exactly and the actual returned name must match by casefold. These guards
run before any ledger creation. The expected name cannot stand in for a missing
returned name. Never relabel a response to make it pass. Expectation metadata is
retained in the capture receipt; it does not create a second source-price point.
Optional per-entry sourceObservedAt/sourceWindowStartAt/sourceWindowEndAt are
retained only when actually supplied from evidence. They are never inferred from
windowDays, capture completion, import/build time or a daily date boundary.

RETAINED RETURNED FIELDS
Provider item ID/name; positive sale median; positive integer source sale count;
reported rolling window; currency; stat_roll presence/null/exact label; actual
item capture time and its precision; supplied source clocks/window bounds;
listings_now; cheapest_listing price_each/channel/room. Every retained listing
explicitly has availabilityConfirmed:false: a returned receipt does not verify
that a shop remains open, especially during maintenance. Listing offers stay
separate from the sale median. Arbitrary owner/sender/token fields are discarded.
No listing is claimed current after its capture, and no owner identity is needed.

Only price_basis == median of sales enters eligible observations. Asking/no-sale
results are excluded with reasons. An identity-verified explicit no-sales response,
including a documented asking fallback with sales_counted0, counts as a completed
attempt without becoming a sale price. Errors, unknown items, missing returned IDs,
auth failures and timeouts remain missing, never zero-priced observations.
Duplicate IDs/names, invalid windows/counts/rolls/listings and inconsistent clocks
are rejected. Capture times must be nonfuture and within any declared batch span.

IMMUTABILITY AND HISTORY IDENTITY
- Append-only captures and observations, linked by receipt identity. Replaying
  an identical capture does not duplicate records or rewrite an unchanged view.
- An item+actual-capture-time conflict rolls back transactionally; it is not an
  overwrite. Later captures preserve earlier prices. Older receipts can be added
  without regressing the current projection. Ledger commits before projection;
  replay can repair a local projection-write failure.
- variantKey hashes source + item ID + reported roll status/exact label.
  unknown_legacy, reported_null and an explicit label are distinct identities.
- seriesKey additionally includes the reported window definition and sale basis.
  A7-ATT and10-ATT glove do not become one quality-constant history. A3-day and
  4-day estimate are explicitly different measurement series.
- Every observation declares qualityConstant:false. Even a repeated label does
  not establish full stat equivalence, quality adjustment or independent samples.
- variant_history(db_path, variant_key, series_key=None, limit=500) reads indexed,
  bounded private observations. Use series_key for one fixed-window series.
  Neither stat values nor missing roll labels are reverse-engineered.

LEGACY DATA
On the first actual import, the existing accepted projection is retained in the
private ledger. Its known prices/counts/windows and original capture timestamp
remain intact. A discarded legacy stat_roll cannot be reconstructed: it remains
unknown_legacy, not clean, not reported-null, and not an exact per-item clock.
No production migration/import was performed in this readiness task.
Legacy projection metadata can be normalized in memory for a report without
rewriting its capture file or creating the private ledger.

SEPARATE ROLLING-INDEX COMPARABILITY GUARD
The daily basket contains aggregate gear prices without a matched provider roll
baseline. The rolling MPI comparison now excludes captured Equipment, equipment
Weapon IDs, and any explicitly reported roll without a matching daily baseline.
Fungible Materials/Consumables/Scrolls and non-equipment Weapon IDs can remain
eligible. Cash instead compares price with its known fixed NX purchase cost, not
with a daily baseline: explicit null or exact provider Clean is eligible; other
labels can include an upgrade premium, and missing legacy roll metadata remains
unverified. Unknown category/variant scope is not guessed.

rollingReference.comparison reports methodVersion3, capturedBasketCoverage,
comparableBasketCoverage, comparable item counts, every excluded item/weight and
its reason. It does not silently equate captured coverage with comparable coverage.
The existing80% rolling-MPI threshold still applies to comparable weight.
The primary fixed MPI, fixed cash index, NX headline, membership and weights are
not changed. This is only a conservative guard on the separate rolling reference.

AGGREGATE HISTORY / WORKER COMPATIBILITY
Aggregate history remains one point per measured capture/method, never one row
per variant. Measurement hashes exclude pull clocks and current-listing changes;
an unchanged median/count/window/roll does not become a fictitious independent
measurement merely because another pull occurred. Existing same-time points are
not overwritten to retrofit the new method. Older aggregate rows retain their
original values and may lack roll identity; that limitation is explicit metadata.
New metadata stays inside rollingReference / rollingReferenceHistory, already
covered by the existing Worker reference fingerprint. No runtime upload route,
Worker history-key change, top-level variant array or source gate is introduced.

PUBLICATION COMPLETENESS GUARD — CURRENT BEHAVIOR
+ import_capture verifies payload.planHash against the integrity-checked frozen
  incoming/scanner-capture-plan.json. Every planned target needs one identity-
  verified sale or explicit ineligible/no-sales response before replacement.
+ Valid zero-sales/asking-fallback responses count toward target completeness but
  never supply an asking price as a sale. Unknown/auth/error/timeout/no-ID returns
  stay missing. Wrong positive returned IDs/names remain fatal identity mismatches.
+ Partial successes can be archived by an explicit import, but the current selected
  price projection stays BYTE-IDENTICAL. It never fills missing items from older
  captures under a new timestamp. A full new plan intentionally changes target
  scope; old v1-mix observations remain in the append-only ledger.
+ A completely attempted all-no-sales batch is archived receipt-only, retains the
  last-good projection and does not invent zero prices. With no verified usable
  receipt at all, a failed pilot creates no price ledger.
+ Legacy unplanned imports must account for prior-projection IDs plus declared
  requested IDs. A subset cannot drop other last-good items. A first unplanned
  valid capture establishes only its actual local scope, never whole-market scope.
+ The ignored incoming/rolling-intake-status.json reports published/held/rejected,
  reason, verified/eligible/ineligible/missing counts, planned hash, incoming capture
  time and unchanged/published projection capture time. import_capture returns this
  as intakeStatus; it is not a new market observation. CLI output distinguishes
  stored sale receipts from published projection rows. Snapshot clocks remain dated.
